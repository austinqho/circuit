# G5 limits (what this evidence does not show)

1. **Codex never ran.** Part A is a script following the skill literally: it derives the annotation evidence with a reimplementation of Codex's anchor builders (research note §1, read from the shipped bundle, not observed running), runs the skill's DOM lookup, and calls the MCP. Whether Codex's model, given the skill, chooses the same calls in the same order, and whether its browser tool can evaluate the lookup snippet in the IAB, is Part B (`docs/G5-RUNBOOK.md`). The handoff's clause "In Codex's IAB … Codex returns" is not reached by this directory.
2. **The failure is seeded.** No genuine 4xx fits "succeed, fail, succeed, then annotate" on anything-llm without an LLM key (gate §3.1). The 422 comes from the G6 seed in the update handler. Everything Tracer reports about it (request, route, status, handler spans, frontier) is recorded, not seeded; but the demo only works because that handler returns a 4xx. The genuine alternative is the single-user login with a wrong password (401 from `POST /request-token`), which cannot end with the element on screen after a successful attempt.
3. **The UI already says why.** The seeded handler's message reaches the page ("Error: Invalid workspace name.", `run/step-05-rename-attempt-2.png`). Tracer adds which attempt failed, the request, the route, the status and which handlers ran; it cannot show which line in the handler returned the 422: anything-llm persists through Prisma/SQLite, which Tracer does not instrument, so every chain stops at `handler` (G6 LIMITS 1). The agent still has to read `server/endpoints/workspaces.js` to find the cause.
4. **Codex's pick is the button's label, not the button.** Gate off, Codex's target climbs to the first ancestor that is interactive *or* has text and is at least 24×16 px, which here is the `<div>` inside the `<button>`. The key is found through `closest('[data-tracer-el]')`. If Codex's real text rule differs (own text vs. subtree text), the pick could be the button itself; the lookup handles both (tests). The builders mark as [inference] what the note does not state: `:nth-of-type` is always emitted; ids outside `^[A-Za-z_][A-Za-z0-9_-]*$` are not emitted as `#id`.
5. **The annotated element is re-rendered.** *Update Workspace* only renders while the form has unsaved changes, so the session types one character before annotating; each attempt mounted a new button node. The key is the same across those mounts because it is the placement plus a DOM-order ordinal (G3 second pass). A layout where another `CTAButton` renders before it on some mounts and not others would change the ordinal and split the history across keys.
6. **The component is the button's own JSX site.** `resolve_element` answers `CTAButton` at `components/lib/CTAButton/index.jsx:8`, where the `<button>` is written. The place a developer would call "the Update button" (`<CTAButton type="submit">` in `GeneralAppearance/index.jsx:55`) is not reported: G3's `binding_placement` is only recorded when that outer placement binds a handler, and this one binds none (the form's `onSubmit` does). The entry handler answer (`handleUpdate`, line 26) is where the developer's code runs.
7. **Three G4 behaviours changed for this gate** (gate §10): repeated request-bearing submits of one form are separate episodes in the store (the M1 viewer still groups them); `element_history` gained `attempts`; the no-key fallback accepts an ancestor tag. The G4 grader on final7 (81/81) and the G6 grader on the G6 store (6/6) give identical results, and neither store contains a split episode, so the split rule has been exercised on this run and on unit tests only.
8. **Store run row without source.** The collector writes the run row on SIGTERM without `source` (commit, clean) or `steps`; the harness's in-process writer (G6) recorded both. `runs.jsonl` here has `source: null, steps: []`; the fixture commit is in `fixture-state-before.json` and the step windows in `run/coverage.json`.
9. **Rows before the collector.** The parity and smoke page loads ran before the collector started; their rows were posted by the sink, failed, and were counted as dropped on those pages, not stored (the harness does not read those pages' stats). 348 backend spans from those loads are in `run/spans.jsonl` and not in the store. The session page's sink lost nothing (0 dropped, 1 retry).
10. **One run, one element, one question.** Rendering ordinals, the Codex selector and the fallback ranking were exercised on this page only. The fallback returned 3 candidate targets; on a busier page it would return more, still never a pick.
11. **Built, not dev-served.** The app is a production build served by the harness; `vite dev` with the plugin is not exercised (G2 builds only). OAI declarative attributes were absent (`oaiAttributes` default `detect`, no `document.oai` in headless Chromium), which is the expected state while OpenAI's gate is off.
12. **Grader independence.** `test/g5-grader.mjs` shares no code with `analysis/`, `collector/` or `mcp/`, but the implementing agent wrote it. Its attempt grouping ("each submit on the element closes an attempt") is simpler than the store's episode rule and agrees here; a separate agent should rerun it.
