### 1a. Why step 2 and several controls read as "unassigned": evidence loss in the capture channel

This is the single most important finding of this cycle and it is a harness/capture defect, not a joining defect.

- `records.jsonl` contains 21,410 rows, but the runtime's `sequence` counter reaches 294,660. 273,250 emitted rows (92.7%) are absent, in 550 gaps, 233 of them ≥ 200 rows. Example: sequences 64,328–70,025 (the entire click → `ChatForm` submit → `ask` → fetch path of the step-2 send, 10:05:50.407 → 10:05:50.873) are missing.
- Cause (harness line 76): each row is shipped with `navigator.sendBeacon('/__capture', text)` inside `try {} catch {}`. `sendBeacon` returns `false` and drops the payload when the per-page beacon queue is full; the return value is ignored. Bursts of `function.enter/exit` rows saturate it.
- Consequence for `dom.action`: 103 of the 230 actions in `chains.md` have no `dom.action` row (127 do). Those 103 are exactly the "Scripted step unassigned" section plus the `dispatch_evidence_removed` stops. The harness recovers only `network.request` rows from the in-page buffer (`__productTraceRuntime.records`, "buffer_added 60"), so requests survived (56/56 wrapper gate) but the click rows that own them did not.
- Consequence for step grouping: `step_action_ids` is computed as `dom.action` rows with timestamps between consecutive scripted notes (harness line 170). An action without a `dom.action` row cannot be assigned to any step. That is why `mucids8l:64855` (the send click, which owns the step-2 POST and all of the step-2 writes) is unassigned and its chain terminates in `dispatch_evidence_removed`, while step 2 is credited only with the New-chat click's reads.
- `LIMITS.md` and `RUN.md` do not mention this loss; `chains.md` says "Full enter/exit rows remain in records.jsonl", which is not true for this capture.

The joiner behaved correctly given the rows it had: it did not invent a click for `mucids8l`, and the negative replays show the stop is honest. But the M1 deliverable ("one record per user action") is not met for the send click in this capture because the click itself was not recorded.

**The 20 boot requests on the login submit.** Decision: they are causally downstream of the login submit, not independent, and the attribution is correct under M1's continuation rule; what is missing is a semantic distinction, not a causal one. Justification from the raw rows:

- Before login, the page-load requests at 10:05:39.294–39.343 (`GET /api/config` ×2, `POST /api/auth/refresh`, `GET /api/banner`) are recorded with `reason: unattributed_transport` and `action_id: null`. So the runtime does not attach page-boot traffic to an action when no action owns the continuation. This is the negative control and it passed.
- The 20 GETs all carry `parent_continuation_id` = `continuation:action:mucidkhg:1383:promise:NNN`, i.e. they were issued from promise continuations registered under the submit action, and they all start ≥ 142 ms after the `POST /api/auth/login` response window (first at 10:05:40.627; login server span ended 10:05:40.561).
- The request spines name the path: `/api/banner` has spine `Auth/mutations.ts onMutate` → `useClearStates.clearStates` → `Auth/mutations.ts onSuccess` → `AuthContext.tsx onSuccess` → `AuthContext.tsx setUserContext` → `getBanner` → `_get`. That is the login mutation's success callback setting auth state, which navigates to `/c/new` and mounts the chat surface whose queries fire. Without the login response none of these would have fired at that moment.
- `/health` (10:05:41.792) has spine `connection.ts useEffect` → `setTimeout` → `performHealthCheck` → `healthCheck` → `_get`: a timer armed by an effect that ran because `isAuthenticated` flipped. Causally downstream too, but this is the case that will leak: any interval armed in that effect will keep inheriting the login action for the life of the page. Only one `/health` occurred in this 48 s session, so the leak is a risk, not an observation.
- Verdict: `coverage.json`'s label `independent_boot_rows_observed_under_login_action: 20` is wrong in the causal sense; the rows are dependent. The correct statement is "20 mount-effect requests downstream of login, distinct from login's own effect (sessions.insert)". Distinguishing an action's effect from its downstream page mount is a policy/semantic layer (M2-adjacent), not an M1 join error. The uncommitted working-tree copy of `src/runtime-attribution-browser.js` adds a `linkage_kind: direct | mount_effect` field for exactly this; the committed runtime that produced this capture does not have it (no `linkage_kind` on any row).

Side observation on spines: later boot requests accumulate sibling function ids that are not their ancestors (e.g. the `/api/tags` spine includes `getRole`, `getUser`, `getFavorites`, `listProjects`). The spine is therefore "functions active in this continuation lineage", not a strict causal call path. Joins never use it, so nothing in this grade depends on it, but it should not be presented as a call stack.
