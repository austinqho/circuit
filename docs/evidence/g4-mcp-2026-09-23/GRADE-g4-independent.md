## Findings (none blocks G4)

- **F1: evidence drift.** `GRADE-g4.md` (rev1) records `send vs agent-chat: path_changed=false` (parameters_only). That no longer describes the code. rev2 added `GRADE-g4-rev2.md` and amended the gate. Anyone citing `GRADE-g4.md` for `compare_chains` should cite rev2 or this file instead.
- **F2: `__proto__` in raw JSON arguments is dropped, not rejected.** `{"action_id":"action:mud8sc1x:9","__proto__":{"x":1}}` returns `ok`. `{"__proto__":{"action_id":…}}` returns `invalid_input: missing required property "action_id"`, so an inherited value is never used and nothing is polluted. Gate §3 says `__proto__` "is rejected", which holds for the tool name but not for this argument key: the key disappears before the own-property check, probably during the SDK's argument parsing. `constructor` as an extra key is rejected correctly.
- **F3: a fallback key can span several DOM elements, and one credit is async-only.** Key `handler:…32f0c87d…:8036:8424|input` (`AgentSelect.tsx`) lists `action:mud8t53x:26` (Instructions textarea) and `action:mud8t518:24` (Agent name input). In the raw rows, that function is entered in action 24 only with `invoked_by:"async"`, never `"event"`, yet `action_chain` reports `rooted: true` for it. The credit comes from `indexEntryHandlerUnits`, which the gate forbids reimplementing, and it is outside the 9 graded flows. `handler_placement` confidence correctly says the key is not an element. However, `element_history` on that key mixes two elements, and one of the entries is weakly supported.
- **F4: a selector `#id` that no recorded target states is not a mismatch.** `span#zzz-not-here` and `textarea#zzz-not-here` return `ambiguous` with a tag-only candidate (score 1), and `mismatched` does not mention the id. This meets the contract (never a pick), but the result would read better as `not_found`, or at least list the unmatched id in `mismatched`/`ignored`.
- **F5: `different_handler` never sets `path_changed`.** The code excludes every `entry_handler` stop from `path_changed`, which matches the §3.2 formula. The prose, though, only exempts `source_revision`. Example: send vs regen2 has entry `different_handler` (ChatForm → ContentRender) and `path_changed: false`. For G6 on a frontend-only store, a fix that rebinds the element to a different handler without changing the request would read "unchanged".
- **F6: middleware DB reads are not stops.** 36 DB spans sit under the server span but under express *middleware* spans (`requireJwtAuth`, `checkBan`, `validateConvoAccess`, `buildEndpointOption`) rather than a handler span. They appear in 8 of 9 flows and are all `find` reads. They are not reported. The write sets are unaffected. This follows the gate's handler-descendant rule; it is an under-report, not an invention.
- **F7: protocol edge cases.** A non-JSON line is silently ignored (no -32700). Missing `params` returns -32603 instead of -32602. Both come from SDK behaviour and neither crashes.

## 6c: my view on the G6 use case

A different concrete path under the same route template should count as a path change unless the differing segment is an entity identifier. `openAI` vs `agents` fills `:endpoint`, which picks a different endpoint implementation inside the same `controller`. The express handler chain and the DB op set look identical here, but the code that runs below the controller differs, and an agent claiming "my fix changed the runtime path" should get credit for that. Rev1's route-template rule would have hidden it. So rev2's call, `different_value` with `path_changed: true`, is right, and `parameters_only` should be kept for id-shaped segments.

The residual risk is the id heuristic: 24-hex, UUID, 8+ hex and digits. LibreChat's own agent ids (`agent_YAQ8Y1HJYBF3MirpqmkeZ`, nanoid) are not id-shaped. A before/after reproduction that creates a fresh agent and then hits `/api/agents/<id>` would therefore report a false `path_changed: true`. G6 should either reproduce against the same entity or use the server route template as a tiebreak when the differing segment sits at a `:param` position that is not the route's dispatch parameter. final7 has no pair that differs only in id-shaped segments, so `parameters_only` is untested on real data.
