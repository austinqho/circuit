## 6. Final assessment

What the final drive proves about "every interaction pattern gets logged properly": for the interaction patterns the scripted flow actually performed, Tracer's capture is lossless (370/370 rows, sequence 1–370 with no gaps, 0 detached dispatches), every first-party API request is stamped with the `dom.action` that caused it, every backend span joins to that request by exact trace id and W3C parent (97/97 server spans, 558/558 db spans, 0 orphans, 0 false joins), and every Mongo write for the user in the window — 13 write sets across sessions, conversations, messages, transactions, sharedlinks, aclentries and the delete cascade — is confirmed to the millisecond under its own causing action, with no write attached to a bystander and no silent write. Six of the eight gate mutations (send, feedback, regenerate, edit-resubmit, rename, delete) are proven end to end, and the cycle-5 edit defect is fixed (the resubmitted text now differs). What it does not prove: that the agent-create pattern is logged (it never happened — no `POST /api/agents`, no `agents` document, the panel still reads "Create New Agent"; `reached_db: true` rests on panel-open reads, so the gate predicate must require a write span); that agent-chat is an agent chat (it hit the openAI endpoint with no agent); that the per-unit ledger measures coverage of interaction patterns at all — its 30 reached_* outcomes are 2 real and 28 fabricated by dumping the whole request log onto never-dispatched units, its `correct_stop` credits 9 of 30 units with a dispatch of a different event, its `unreachable` reasons are mostly single probes under a modal and in two sampled cases are contradicted by the screenshot (`duringRunAction` visibly rendered) or by the ledger itself, and its `not_encountered` marks as "never rendered" components that Tracer's own rows show being rendered and used (RenameForm, ChatDirection, LoginForm) while the eleven write-bearing actions outside the gate/unit overlap are credited to no unit. The single biggest cause of the gap, with evidence: **the ledger's unit-to-behaviour link is a static identity match on fiber props, not execution.** The bundle contains no `function.enter` rows and empty `spine.function_ids` on all 144 actions, so "encountered", "unreachable" and "correct_stop" were all decided by whether a handler's compiled identity could be found on a live fiber at a state checkpoint; where that match fails the unit falls to `not_encountered` (RenameForm rendered and typed into, `:25`/`:26`; `ChatDirection:349:422` vs its runtime-only twin `…:935:935` that got the credit; 61 identities still static-only; 22 runtime-only units that are hash-duplicates of static ones), and where no dispatch links a unit to an action the chain builder falls back to attaching every request in the run (27 null-action `reached_request` units). Until the ledger keys on execution — a `function.enter` under the action's continuation, which the smoke gate shows the runtime can emit (`enters: 1`, `same_action: true`) but the drive did not record — the per-unit numbers cannot be read as coverage, and the honest claim is the narrower one the request-level evidence supports: every request and write that occurred was attributed correctly; whether every interaction pattern occurred is not yet measured.
