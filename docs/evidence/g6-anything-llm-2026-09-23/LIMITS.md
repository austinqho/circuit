# G6 limits (what this evidence does not show)

1. **No DB stop, ever.** anything-llm persists through Prisma/SQLite, and Tracer has no adapter for either. Every chain in this store stops at `handler` ("no database span descends from the admitted handler span"). The seeded 422 therefore shows as an HTTP status change at the route stop and in the outcome. It does not show as a missing `update workspaces` write. The handoff's §3.2 example ("After: → 200 → `users.update`") is not reproducible on this repo. In B, the handler spans are identical to A: the bug returns from inside the same anonymous update handler, so the Express handler list does not change. The frontier text is generic ("no database span…"). Unlike the G2 harness's per-repo note, it does not say "Prisma is not instrumented", because the package has no product list.
2. **One action, one repo.** G6 was exercised on one user action: the workspace-rename submit, replayed six times. The whole 8-step session ran each time. The remap was exercised on real builds for one file (`GeneralAppearance/index.jsx`, 4 functions). The negative controls are synthetic unit tests (`test/compare-remap.test.mjs`): rebinding to another function in an edited file gives `different_handler`, a changed function structure gives `unmapped_revision`, and two functions in one build give `different_handler`. No real run rebinds an element to a different handler.
3. **The remap is structural, not semantic.** It maps by pre-order position among a file's manifest functions and requires an equal nesting shape. Its known failure modes:
   - Moving a function to another file, or adding or removing any function in the edited file, yields `unmapped_revision`. That counts as a path change: a false alarm, never a false "unchanged".
   - Swapping the *bodies* of two same-shaped functions while keeping every element's binding would still be reported as `source_revision` for each. The backend stops would still expose a behavioural change.
   - The remap does not look at function names. Manifests carry none.
4. **`source_revision` for E, and the frontier word.** In E the early return is inside the same function, so the entry handler is (correctly) a `source_revision`. The path change comes from the removed request/route/handler stops. The after-side frontier reads `stopped_at: validation` ("the submit produced no request and the same form mutated"). That is the G4 vocabulary for a submit with no request followed by a mutation on its form. The mutation here is the button label switching to "Updating…", because `setSaving(true)` ran before the early return. The frontier does not literally say `stopped_at: handler`.
5. **Build id granularity.** The build id covers the set of first-party function ids. A frontend change confined to a file with no functions (a constants module, CSS, `index.html`) would not change the build id. Backend-only changes (A, B, C) share one build id; runs, not builds, separate them. `runs.jsonl` records the fixture commit per run for that reason.
6. **Stored manifests keep a bundle-local `index`.** The store writer used for these runs kept each manifest row's runtime `index`. Each build's manifest was written by the first run of that build: A for `b-2dc9…`, D and E for theirs. Runs B, C and C-fix-r2 numbered the same functions differently (4,828 / 4,857 / 4,909 of 5,101 positions differ from A). Nothing in the store reader, the MCP or the grader reads `index`; rows join by `function_id`. The writer was amended afterwards to drop `index` (gate doc §3.1). This evidence was not rewritten.
7. **Selection of "the same action" uses a step window.** The replayed action is chosen by the harness (event `submit` inside the `rename-workspace` step window). Timestamps pick the action; they never attach evidence. The package never matches actions across runs by itself. `compare_chains` takes two explicit action ids.
8. **Source lines for older builds are `stale_build`.** The comparisons ran with `--source-root` at the restored `ad97bc8d`. Chains from builds D and E therefore report `line: null, line_status: "stale_build"` for the edited file. That is correct: the checkout no longer matches those builds. The `AGENT-READS.md` rendering then shows `file@start-end`.
9. **Grader independence.** `test/g6-grader.mjs` shares no code with `analysis/`, `collector/` or `mcp/`, but it was written by the implementing agent. Its entry-handler check uses "the first depth-zero `function.enter` of the submit". That agrees with the effect-rooted credit here, but it is a simpler rule than `indexEntryHandlerUnits`, and on other actions the two can diverge. A separate agent should rerun it.
10. **Not driven through a coding agent.** The "agent's fix" and the refactor were applied by this harness session as scripted commits. No Codex/Claude Code session read the MCP output and made the fix. `AGENT-READS.md` shows what such an agent would read.
11. **Store placement.** The store lived at `<fixture>/.tracer`. The fixture does not gitignore it, so the harness's source-clean check excludes exactly that path (the unfiltered status, `?? .tracer/`, is recorded per run).
